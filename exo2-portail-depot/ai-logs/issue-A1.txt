     Module auth JWT — connexion avocat

     Contexte

     Le portail a désormais un besoin métier défini (CLAUDE.md § Context) : côté
     avocat, tout est
     authentifié — créer une demande de dépôt, générer un lien expirable à PIN,
     consulter le
     dashboard. Côté client, tout est anonyme. Aucune de ces routes n'est
     écrite, et rien ne
     peut l'être tant qu'il n'existe pas de moyen de savoir qui est l'avocat qui
     appelle l'API.

     Le backend est encore le template NestJS nu : AppModule n'importe rien, il
     n'y a ni
     ConfigModule, ni base de données, ni validation d'entrée.

     Ce chantier livre la brique manquante : un module auth qui authentifie
     l'avocat par
     e-mail + mot de passe et pose une session JWT, plus le JwtAuthGuard que
     toutes les futures
     routes avocat viendront décorer.

     Référence adaptée : ~/delivery/eip/VigilArt/backend/src/auth/. Trois écarts
     assumés,
     détaillés plus bas — pas de base de données, pas de client mobile, pas de
     refresh token.

     Arbitrages retenus (validés)

     Sujet: Source des identifiants
     Choix: Compte de démo unique, seedé depuis l'env
     Pourquoi: Pas encore de base. Une interface UsersService.findByEmail()
     isole ce
     choix : le jour où Prisma arrive, seule l'implémentation change.
     ────────────────────────────────────────
     Sujet: Mot de passe de démo
     Choix: Hash bcrypt en .env (AVOCAT_PASSWORD_HASH)
     Pourquoi: Le clair n'existe nulle part sur disque. Produit par pnpm 
     hash:password, qui lit le mot de passe au clavier (jamais en argument —
     l'historique du shell le garderait).
     ────────────────────────────────────────
     Sujet: Transport du token
     Choix: Cookie httpOnly seul
     Pourquoi: Front et API partagent une origine (proxy nginx :8080), donc
     aucun
     CORS à configurer et le token est hors de portée d'un XSS. Rien dans le
     corps
      de réponse.
     ────────────────────────────────────────
     Sujet: Périmètre
     Choix: login + logout + me + JwtAuthGuard
     Pourquoi: Le guard est la vraie livraison : sans lui, le token ne protège
     rien.
     me permet au SPA de rétablir sa session au rechargement.
     ────────────────────────────────────────
     Sujet: Refresh token
     Choix: Écarté pour l'instant
     Pourquoi: VigilArt persiste les refresh tokens hachés en base pour pouvoir
     les
     révoquer. Sans base, un refresh non révocable de 7 jours serait plus 
     faible
     que le seul access token. À reprendre avec la base.
     ────────────────────────────────────────
     Sujet: Client mobile
     Choix: Écarté
     Pourquoi: VigilArt a une app mobile, pas ce portail. loginMobile /
     JWT_MOBILE_REFRESH_EXPIRES ne sont pas repris.

     Dépendances à ajouter (backend/)

     @nestjs/config, @nestjs/jwt, @nestjs/passport, passport, passport-jwt,
     bcrypt,
     cookie-parser, class-validator, class-transformer, @nestjs/throttler
     — dev : @types/passport-jwt, @types/bcrypt, @types/cookie-parser.

     ⚠️ bcrypt est un module natif. pnpm 11 rend les scripts de build opt-in :
     il faudra
     ajouter bcrypt à allowBuilds dans backend/pnpm-workspace.yaml (pnpm 
     approve-builds),
     sinon pnpm install --frozen-lockfile sort en 1 sur ERR_PNPM_IGNORED_BUILDS
     — y compris
     dans le Dockerfile, qui COPY déjà ce fichier. À vérifier par un build
     d'image, pas seulement
     en local. Repli si la compilation native pose problème en image Alpine/slim
     : bcryptjs
     (pur JS, hashes $2b$ interchangeables).

     Variables d'environnement

     .env.example porte aujourd'hui les variables recopiées de VigilArt. À
     réécrire :

     # Compte avocat de demo (le hash se genere avec : pnpm -C backend
     hash:password)
     AVOCAT_EMAIL=
     AVOCAT_NOM=
     AVOCAT_PASSWORD_HASH=

     # JWT
     JWT_SECRET=
     JWT_EXPIRES=2h
     SALT_ROUNDS=12

     Retirées : JWT_REFRESH_SECRET, JWT_REFRESH_EXPIRES,
     JWT_MOBILE_REFRESH_EXPIRES
     (sans objet sans refresh token ni mobile). .env.example ne contient que des
     placeholders
     vides — jamais de valeur d'exemple qui finirait copiée telle quelle en
     production.

     JWT_EXPIRES=2h plutôt que le 15m de VigilArt : sans refresh token,
     l'expiration est une
     déconnexion sèche. 15 min est intenable pour un avocat qui monte un dossier
     ; 2 h est le
     compromis assumé jusqu'à ce que le refresh existe.

     Validation au démarrage (ConfigModule.forRoot({ validate })) : JWT_SECRET
     absent ou
     trop court, AVOCAT_PASSWORD_HASH qui ne ressemble pas à un hash bcrypt →
     l'application
     refuse de démarrer, avec un message nommant la variable. Sans ça, la panne
     se découvre au
     premier login, en 500, en production. Se branche naturellement sur le
     .catch(...) déjà
     posé dans main.ts (exit 1, message explicite).

     Points de conception qui comptent

     Énumération d'e-mails. VigilArt retourne immédiatement quand findByEmail
     est vide, et
     ne fait le bcrypt.compare que si l'utilisateur existe. La différence de
     temps de réponse
     (bcrypt à 12 rounds ≈ 100 ms) permet à un attaquant de distinguer « e-mail
     inconnu » de
     « mot de passe faux ». Correctif ici : comparer systématiquement contre un
     hash factice
     constant quand le compte n'existe pas, pour que les deux chemins coûtent le
     même temps.
     Même message (Identifiants invalides), même statut (401), même durée.

     Rate limiting. Un portail public avec un seul compte est la cible de
     bruteforce
     idéale. @nestjs/throttler sur /auth/login uniquement (ex. 5 tentatives /
     minute / IP).
     Le proxy nginx renseigne déjà X-Forwarded-For — il faudra donc
     app.set('trust proxy', 1),
     sans quoi toutes les requêtes semblent venir de l'IP du conteneur nginx et
     le quota est
     partagé par tout le monde.

     Le hash ne sort jamais. Types séparés Avocat / AvocatPublic plutôt qu'un
     delete user.password : c'est le compilateur qui garantit qu'un hash ne peut
     pas atterrir
     dans une réponse, pas la vigilance. Aucun log ne contient e-mail + mot de
     passe.

     Cookie. httpOnly, sameSite: 'lax', secure si NODE_ENV=production, path: '/'
     (pour qu'il parte aussi vers /api/...), maxAge aligné sur JWT_EXPIRES. Le
     logout
     efface avec exactement les mêmes options, sinon le navigateur ne fait pas
     correspondre
     le cookie et ne l'efface pas.

     Le lint est bloquant (--max-warnings 0, recommendedTypeChecked).
     passport-jwt et
     son PassportStrategy déclenchent facilement no-unsafe-argument /
     no-unsafe-call. Ces
     warnings sont à traiter par un typage correct, pas par un élargissement de
     l'ignore
     (cf. CLAUDE.md). C'est le point le plus susceptible de coûter du temps.

     Tests e2e (backend/test/auth.e2e-spec.ts)

     Le beforeAll pose les variables d'env de test — hash calculé à l'exécution
     par bcrypt
     à partir d'un mot de passe constant local au fichier, et JWT_SECRET de test
     généré par
     randomBytes. Aucun secret sur disque, aucun .env.test (qui serait de toute
     façon capté
     par .env.* dans .gitignore).

     Limites connues, à écrire noir sur blanc

     - Le logout est côté client seul. Effacer le cookie n'invalide pas le JWT :
     un token
     copié avant la déconnexion reste valable jusqu'à son expiration. Une
     révocation réelle
     demande une liste de tokens révoqués — donc une base. À dire dans le
     README, pas à laisser
     croire.
     - Un seul compte, en env. Pas d'inscription, pas de réinitialisation de mot
     de passe,
     pas de multi-cabinet. Assumé tant que la base n'existe pas.
     - Pas de refresh token : au bout de JWT_EXPIRES, l'avocat se reconnecte.
     - Le compte de démo est un compte de démo : il ne doit pas survivre à une
     mise en production
     réelle.

❯ Est-ce une bonne pratique d'avoir un lint bloquant côté back et front?        

● Réponse à ta question au passage, puis le plan.

  Oui, c'est une bonne pratique — mais ce qui la rend bonne, c'est le quand, pas
  le où. Un lint bloquant règle un problème précis : un warning non bloquant
  est un message que personne ne lit. Il s'en accumule dix, puis cent, et le
  signal disparaît dans le bruit. À zéro warning toléré, chaque nouveau warning
  est forcément du travail introduit à l'instant, par la personne qui sait
  encore pourquoi.

  Les deux objections sérieuses :

  - Ça bloque sur du cosmétique. Vrai si le lint mélange règles de style et
  règles de correction. Ici c'est atténué : Prettier gère le style, et
  l'essentiel de ce qui reste (no-floating-promises, no-unsafe-argument) signale
  de vrais bugs. Un await oublié sur un upload n'est pas du cosmétique.
  - Ça pousse à élargir les ignores. C'est le vrai risque, et il est déjà
  documenté dans CLAUDE.md. La discipline est de neutraliser ligne à ligne avec
  une justification — comme les deux oxlint-disable-next-line de color-mode.tsx
  — jamais un fichier ou un dossier entier.

  Deux réserves honnêtes pour ce projet : le lint n'est bloquant qu'en local
  tant qu'il n'y a pas de CI (D3), donc il repose sur ta discipline ; et une
  montée de version d'eslint ou d'oxlint peut ajouter des règles et casser un
  build sur du code qui n'a pas bougé — d'où les versions épinglées à l'exact
  côté frontend.

  Maintenant le plan A1.

     │                                                                         │
     │ Conformité ACID et intégrité stricte des données. Ce n'est pas un       │
     │ argument générique ici :                                                │
     │ le domaine est le dépôt de pièces juridiques, où une donnée à moitié    │
     │ écrite est un dossier                                                   │
     │ faux. Trois endroits du produit en dépendent directement.               │
     │                                                                         │
     │ - Un dépôt de pièce écrit un objet dans MinIO et une ligne de           │
     │ métadonnées (A3/C2). La                                                 │
     │ transaction garantit qu'on ne se retrouve pas avec une pièce comptée    │
     │ comme reçue alors que                                                   │
     │ le fichier n'existe pas, ni l'inverse.                                  │
     │ - Le statut complète d'une demande se dérive du nombre de pièces reçues │
     │ (B4). Deux dépôts                                                       │
     │ simultanés sur la même demande doivent être sérialisés, pas se          │
     │ recouvrir.                                                              │
     │ - L'intégrité déclarative — clés étrangères, contraintes UNIQUE sur le  │
     │ token public,                                                           │
     │ NOT NULL, types CHECK — fait porter les invariants par la base plutôt   │
     │ que par la                                                              │
     │ discipline du code applicatif. Un token public en double devient        │
     │ impossible, pas seulement                                               │
     │ improbable.                                                             │
     │                                                                         │

● « Sérialisés » veut dire : du point de vue de la base, les deux opérations se
  passent l'une après l'autre, jamais entrelacées. « Se recouvrir », c'est le
  cas contraire — les deux lisent le même état de départ et chacune écrase le
  résultat de l'autre.

  Le cas concret. Demande « Dossier Martin », 3 pièces attendues, 1 déjà
  déposée. Le client sélectionne les deux dernières d'un coup : le navigateur
  envoie deux requêtes d'upload en parallèle.

  t1  requête A : SELECT count(*) ... WHERE request_id = X   →  1
  t2  requête B : SELECT count(*) ... WHERE request_id = X   →  1   (A n'a pas
  encore commité)
  t3  requête A : INSERT sa pièce
  t4  requête B : INSERT sa pièce
  t5  requête A : 1 + 1 = 2 sur 3  →  statut reste "en attente"
  t6  requête B : 1 + 1 = 2 sur 3  →  statut reste "en attente"

  Les 3 pièces sont bien en base. Le dashboard de l'avocat affiche « en attente
  » pour toujours, et il relance un client qui a tout envoyé. L'incrément de B a
  écrasé celui de A : c'est une lost update. Elle ne se reproduit pas en test —
  il faut deux requêtes qui se chevauchent à quelques millisecondes.

  Ce que Postgres apporte contre ça, par ordre de solidité :

  1. Ne pas stocker le statut du tout, le dériver à la lecture. C'est déjà ce
  qu'impose B4 (« statut dérivé, pas saisi »). Il n'y a plus de valeur à
  écraser, donc plus de course. C'est la vraie parade dans ce projet.
  2. Une contrainte UNIQUE (request_id, requested_item_id) : deux dépôts
  concurrents pour la même pièce attendue, la base en rejette un. Le code n'a
  rien à vérifier, et le vérifier ne suffirait pas — entre le SELECT de contrôle
  et l'INSERT, la fenêtre reste ouverte.
  3. Transaction + verrou de ligne (SELECT … FOR UPDATE) pour le seul cas qui
  reste : écrire l'objet MinIO et sa ligne de métadonnées comme un tout
  indivisible.

  Sur ce point précis, ma formulation dans le plan était trop absolue : le
  statut dérivé règle la course de comptage par conception, donc l'argument
  porte surtout sur les points 2 et 3. Je corrige.

● Je reprends plus simplement. Il y a deux idées distinctes dans cette phrase,
  je les sépare.

  Idée 1 — le compteur perdu. C'est le tableau que j'ai montré plus haut. Si on
  stocke un nombre piecesRecues et qu'on l'incrémente en code, deux requêtes
  simultanées lisent la même valeur de départ et écrivent le même résultat. Un
  incrément disparaît. La parade retenue : ne pas stocker ce nombre du tout, le
  recalculer à chaque affichage avec un COUNT. Pas de valeur stockée, rien à
  écraser.

  Idée 2 — la contrainte UNIQUE. Cas différent : le client clique deux fois sur
  « Envoyer » pour sa carte d'identité. Deux requêtes identiques partent. Sans
  garde-fou, on obtient deux lignes pour la même pièce attendue. Le COUNT dit
  alors « 3 pièces reçues sur 3 » alors qu'il en manque une en réalité — la
  demande passe « complète » à tort.

  Le réflexe naturel est de vérifier en code avant d'insérer :

  const existe = await prisma.uploadedFile.findFirst({ where: { requestId,
  itemId } });
  if (existe) throw new ConflictException('Pièce déjà déposée');
  await prisma.uploadedFile.create({ data: { requestId, itemId, ... } });

  Ça ne marche pas. Déroulé de deux requêtes qui se chevauchent :

  requête A : findFirst  →  rien trouvé
  requête B : findFirst  →  rien trouvé      (A n'a pas encore inséré)
  requête A : create     →  ligne 1
  requête B : create     →  ligne 2

  Les deux ont passé le contrôle, et on a quand même deux lignes. C'est ça, « la
  fenêtre ouverte entre les deux » : entre le moment où on lit et le moment où
  on écrit, il s'écoule du temps, et l'état du monde peut changer pendant ce
  temps-là.

  La contrainte UNIQUE (requestId, itemId) déclarée dans le schéma supprime la
  fenêtre : c'est Postgres qui vérifie, au moment exact de l'écriture, de façon
  indivisible. L'INSERT de B est rejeté, l'application reçoit une erreur et
  répond « déjà déposée ». On ne demande plus au code de garantir l'invariant,
  on demande à la base de le rendre impossible à violer.

  Je réécris le passage du plan dans ces termes.

● Concrètement, ça porte sur la granularité du verrou en écriture.

  - Postgres verrouille la ligne. Deux clients qui déposent chacun une pièce sur
  deux dossiers différents écrivent en même temps, sans se voir. Les verrous ne
  se rencontrent que s'ils touchent la même ligne.
  - SQLite verrouille le fichier, c'est-à-dire la base entière. Il n'y a qu'un 
  seul écrivain à la fois pour toute l'application. Une écriture en cours, où
  que ce soit, fait attendre toutes les autres — même sur des dossiers sans
  rapport. Celles qui attendent trop longtemps reçoivent un SQLITE_BUSY.

  Ce que ça change ici : le dépôt de pièce n'est pas une écriture instantanée.
  Il faut pousser le fichier vers MinIO puis écrire les métadonnées. Si ces deux
  opérations tiennent dans une transaction, celle-ci dure le temps d'un upload
  — quelques secondes sur une pièce de 20 Mo depuis un mobile. Pendant ce temps,
  avec SQLite, aucune autre écriture ne passe : un autre client ne peut pas
  déposer, l'avocat ne peut pas créer de demande, aucune tentative de PIN ne
  s'enregistre. Le mode WAL améliore les choses — les lectures ne bloquent plus
  — mais la règle « un seul écrivain » reste.

  Maintenant, la part honnête : à l'échelle réelle de ce projet — un avocat de
  démo, un évaluateur qui clique — cette limite ne se manifesterait probablement
  jamais. Ce n'est pas l'argument décisif. Les deux vrais arguments contre
  SQLite ici sont ailleurs :

  1. La parité dev/prod. Le portail est déployé en conteneurs, et une base
  fichier dans un conteneur veut dire un volume à gérer, une sauvegarde à écrire
  soi-même, et aucun outil standard pour aller regarder les données en
  production.
  2. Le dialecte. Les types de SQLite sont laxistes (CHECK limités, pas de vrai
  timestamptz, typage dynamique). Développer dessus et basculer sur Postgres
  plus tard, c'est découvrir les écarts au moment de la bascule.

  Je corrige le plan pour dire ça, plutôt que de faire porter le choix à un
  argument de charge qui ne tiendrait pas à l'échelle réelle du projet.

● Je reprends en partant du début, sans raccourcis.

  La différence de nature. SQLite n'est pas un serveur : c'est un fichier sur le
  disque, que ton application ouvre directement. Postgres est un programme 
  séparé qui tourne à côté (ici, dans son propre conteneur) et à qui
  l'application parle par le réseau.

  « Un store documentaire » = MongoDB et sa famille. Je l'écarte en une phrase
  parce que ces bases ne savent pas garantir que deux écritures dans deux
  endroits différents réussissent ou échouent ensemble — or déposer une pièce,
  c'est exactement ça : écrire le fichier et sa ligne de métadonnées.

  Ensuite, les trois arguments contre SQLite, un par un.

  1. La parité dev/prod. « Parité » = la base sur laquelle je développe est la
  même que celle qui tourne en production. Avec SQLite en conteneur, trois
  choses deviennent mon problème :
  - le volume — le fichier vit dans le conteneur, qui est jetable ; si j'oublie
  de le monter sur un volume Docker, les données disparaissent au premier
  redéploiement ;
  - la sauvegarde — je dois écrire moi-même le script qui copie le fichier au
  bon moment, alors que Postgres a pg_dump, un outil standard fait pour ça ;
  - l'inspection — pour regarder les données en production, avec Postgres je me
  connecte avec psql ; avec SQLite, il faut entrer dans le conteneur et espérer
  que l'outil y soit installé.

  2. Le dialecte. « Dialecte » = la variante de SQL que comprend chaque base.
  Trois écarts concrets :
  - typage dynamique — SQLite accepte d'écrire le texte "bonjour" dans une
  colonne déclarée INTEGER. Il ne bronche pas. Postgres refuse.
  - pas de timestamptz — pas de type qui stocke une date avec son fuseau 
  horaire. Or l'expiration d'un lien de dépôt est une date : si le serveur et le
  client ne sont pas dans le même fuseau, un lien expire à la mauvaise heure.
  - CHECK limités — un CHECK est une règle déclarée sur une colonne (« ce statut
  ne peut valoir que pending, complete ou expired »). SQLite en supporte moins.

  Le problème n'est pas chaque écart pris isolément, c'est quand on les découvre
  : si je développe sur SQLite et que je passe en production sur Postgres, tout
  ce que SQLite laissait passer casse d'un coup, le jour du déploiement.

  3. Un seul écrivain. C'est le point que je t'expliquais juste avant. SQLite
  verrouille le fichier entier pendant une écriture : tant qu'une écriture est
  en cours, plus aucune autre ne passe, nulle part dans l'application. Postgres
  verrouille seulement la ligne concernée, donc deux écritures sans rapport ne
  se gênent pas.

  Pourquoi ça compte ici : déposer une pièce, c'est envoyer le fichier vers
  MinIO puis écrire ses métadonnées. Ça dure quelques secondes sur un gros
  fichier depuis un mobile. Avec SQLite, pendant ces secondes, personne d'autre
  ne peut rien écrire — ni un autre client qui dépose, ni l'avocat qui crée une
  demande.

  Et l'honnêteté sur ce dernier point : à l'échelle de ce projet, ça 
  n'arriverait jamais. Un avocat de démo et un évaluateur ne produiront pas
  d'écritures simultanées. C'est une limite structurelle réelle, mais ce n'est
  pas elle qui justifie le choix — ce sont les points 1 et 2. Je le dis
  explicitement dans le plan pour ne pas gonfler un argument qui ne tient pas à
  cette échelle.

  Le passage est déjà écrit dans le plan avec cette nuance. Le plan A1 est
  complet : Postgres 17 + Prisma 7, service db avec healthcheck et volume nommé,
  docker-compose.dev.yml pour le dev, migrations jouées à l'entrypoint, et un
  GET /health qui prouve la chaîne par un vrai aller-retour SQL.

     Contexte

     issue_backlog.md § A1, priorité P0. Le portail n'a aujourd'hui aucune
     persistance : le
     backend est le template NestJS nu, AppModule n'importe rien, et
     docker-compose.yml ne
     connaît que backend, frontend et proxy.

     A1 bloque A2, B1, B2, C1, C2 — c'est-à-dire tout le métier. Rien d'utile ne
     peut être
     écrit tant qu'il n'existe pas de moyen de stocker un avocat, une demande ou
     un fichier.

     Ce chantier ne livre aucune entité métier : le modèle de données est
     l'objet d'A2. Il
     livre la plomberie — un Postgres conteneurisé, un ORM branché, une chaîne
     de migrations
     jouée au démarrage — et la preuve que cette plomberie fonctionne de bout en
     bout.

     Critères d'acceptation repris de l'issue :

     - [ ] Service db dans le compose, volume nommé, healthcheck
     - [ ] ORM configuré côté NestJS, connexion lue depuis l'env
     - [ ] Migrations versionnées, jouées au démarrage
     - [ ] Un docker compose up sur machine vierge donne un schéma prêt

     Décisions

     Sujet: SGBD
     Choix: PostgreSQL 17, conteneurisé
     Pourquoi: ACID et intégrité stricte — voir ci-dessous. Image officielle
     postgres:17-alpine.
     ────────────────────────────────────────
     Sujet: ORM
     Choix: Prisma 7 + @prisma/adapter-pg
     Pourquoi: Sûreté de typage, peu de boilerplate, migrations traitées
     sérieusement — voir ci-dessous.
     ────────────────────────────────────────
     Sujet: Première migration
     Choix: Vide de tables métier
     Pourquoi: Frontière nette avec A2. Conséquence à assumer, traitée
     ci-dessous.
     ────────────────────────────────────────
     Sujet: Postgres en dev
     Choix: docker-compose.dev.yml, service db seul
     Pourquoi: pnpm dev continue de tourner sur l'hôte avec son hot-reload.
     CLAUDE.md documente déjà ce fichier comme existant alors qu'il n'a jamais
     été
      créé — l'écart se referme ici.
     ────────────────────────────────────────
     Sujet: Migrations en prod
     Choix: prisma migrate deploy à l'entrypoint du conteneur backend
     Pourquoi: Un docker compose up suffit, sans étape manuelle.

     Pourquoi PostgreSQL

     Conformité ACID et intégrité stricte des données. Ce n'est pas un argument
     générique ici :
     le domaine est le dépôt de pièces juridiques, où une donnée à moitié écrite
     est un dossier
     faux. Trois endroits du produit en dépendent directement.

     - Un dépôt de pièce écrit un objet dans MinIO et une ligne de métadonnées
     (A3/C2). La
     transaction garantit qu'on ne se retrouve pas avec une pièce comptée comme
     reçue alors que
     le fichier n'existe pas, ni l'inverse.
     - Les requêtes concurrentes. Un client qui double-clique sur « Envoyer »,
     ou qui
     sélectionne plusieurs fichiers d'un coup, produit des requêtes qui se
     chevauchent. Vérifier
     en code avant d'insérer ne protège de rien : entre la lecture et l'écriture
     il s'écoule du
     temps, et deux requêtes peuvent passer le même contrôle avant que l'une ait
     écrit. Une
     contrainte UNIQUE (requestId, requestedItemId) déplace la vérification dans
     la base, où
     elle est faite au moment exact de l'écriture, de façon indivisible — le
     second INSERT est
     rejeté, point. Sans ça, deux lignes pour la même pièce feraient passer une
     demande à
     « complète » alors qu'il en manque une.
     - L'intégrité déclarative — clés étrangères, UNIQUE sur le token public,
     NOT NULL,
     CHECK — fait porter les invariants par la base plutôt que par la discipline
     du code. Un
     token public en double devient impossible, pas seulement improbable. Et une
     pièce ne peut
     pas rester rattachée à une demande supprimée.

     Ces garanties écartent d'emblée un store documentaire sans transactions
     multi-documents.

     Face à SQLite, l'argument n'est pas la charge : à l'échelle réelle de ce
     projet, un
     avocat de démo et un évaluateur, SQLite tiendrait sans broncher. Deux
     autres raisons pèsent
     davantage.

     - La parité entre développement et production. Une base fichier dans un
     conteneur, c'est un
     volume à gérer, une sauvegarde à écrire soi-même, et aucun outil standard
     pour inspecter les
     données en production. Postgres apporte les trois par défaut.
     - Le dialecte. SQLite a un typage dynamique, des CHECK limités et pas de
     vrai
     timestamptz. Développer dessus puis basculer sur Postgres, c'est découvrir
     tous les écarts
     au moment de la bascule — au pire moment.

     À noter tout de même, puisque le produit manipule des uploads : SQLite
     n'autorise qu'un
     écrivain à la fois pour toute la base, là où Postgres verrouille à la
     ligne. Une
     transaction qui engloberait l'écriture MinIO plus les métadonnées durerait
     le temps d'un
     upload et bloquerait toute autre écriture pendant ce temps. C'est un
     plafond structurel, même
     s'il ne serait pas atteint ici.

     Face à MySQL/MariaDB, le choix tient à la rigueur par défaut : types plus
     stricts,
     transactions DDL (une migration qui échoue est annulée en entier),
     contraintes réellement
     appliquées.

     Pourquoi Prisma

     - Sûreté de typage. Le client est généré depuis le schéma : une colonne
     renommée casse à
     la compilation, pas à l'exécution. Le lint backend tourne en
     recommendedTypeChecked et
     bloque au moindre warning — un ORM qui renvoie du any y serait un frein
     permanent.
     - Peu de boilerplate. Le schéma est déclaré une fois, dans un fichier
     lisible ; ni
     entités décorées, ni repositories à écrire pour les cas simples.
     - Intuitif. Le schéma se relit sans connaître l'outil, ce qui compte pour
     la section
     « modèle de données » du livrable (H1) : la documentation et la source sont
     le même fichier.
     - Migrations traitées sérieusement. migrate dev génère du SQL versionné et
     relisible,
     migrate deploy le rejoue de façon déterministe en production. C'est
     exactement ce que
     demandent les critères « migrations versionnées » et « jouées au démarrage
     ».

     Contrepartie assumée : une étape de génération à câbler dans le Dockerfile,
     et un moteur de
     requête à préserver au pnpm prune --prod. Les deux pièges sont traités plus
     bas.

     Le point à traiter honnêtement : « schéma prêt » sans aucune table

     Avec un schema.prisma réduit au generator et au datasource, prisma migrate 
     dev ne
     génère aucun fichier — il n'y a rien à migrer. Le critère « un docker 
     compose up donne
     un schéma prêt » ne peut donc pas être prouvé par l'existence d'une table.

     Il serait malhonnête de cocher la case sans preuve. A1 livre donc à la
     place une preuve
     d'exécution réelle : un endpoint GET /health qui exécute un vrai
     aller-retour SQL

     avec

     construit,
     connexion ouverte, requête exécutée. C'est exactement le périmètre d'A1,
     sans empiéter sur A2.

     Cet endpoint n'est pas jetable : il sert ensuite au healthcheck Docker du
     backend, et F1
     (métriques Prometheus) s'appuiera dessus.

     échoue au premier boot. Avec restart: unless-stopped ça finirait par
     passer, mais après
     plusieurs crashs — un démarrage qui « marche en boucle » n'est pas un
     démarrage qui marche.

     3. Le mot de passe Postgres. Jamais en dur dans le compose. .env (déjà
     gitignoré) porte
     POSTGRES_PASSWORD, et le compose l'interpole en
     ${POSTGRES_PASSWORD:?variable requise} —
     la forme :? fait échouer docker compose up avec un message nommant la
     variable, au
     lieu de démarrer un Postgres accessible sans mot de passe. .env.example ne
     contient que des
     placeholders vides.

     4. Ports. La machine de staging est partagée et impose une plage :
     21600-21699, en
     écoute sur 127.0.0.1 uniquement (cf. CLAUDE.md). Publier hors plage ou sur
     0.0.0.0
     casserait le travail d'un autre candidat. A1 n'ouvre qu'un seul port, mais
     l'allocation se
     décide maintenant pour éviter de la reprendre à chaque issue :

     ┌────────┬─────────────────────────────────────────────────────────┬───────
     ┐
     │  Port  │                          Usage                          │ Issue
     │
     ├────────┼─────────────────────────────────────────────────────────┼───────
     ┤
     │ 21600  │ proxy nginx, HTTP (cible du routage par Host)           │ A5/A7
     │
     ├────────┼─────────────────────────────────────────────────────────┼───────
     ┤
     │ 21601  │ proxy nginx, HTTPS (443 en passthrough TLS → nginx      │ A7
     │
     │        │ porte le certificat)                                    │
     │
     ├────────┼─────────────────────────────────────────────────────────┼───────
     ┤
     │ 21632  │ Postgres, développement local uniquement                │ A1
     │
     ├────────┼─────────────────────────────────────────────────────────┼───────
     ┤
     │ 21690+ │ Prometheus / Grafana                                    │ F1/F2
     │
     └────────┴─────────────────────────────────────────────────────────┴───────
     ┘

     En production, db ne publie aucun port : le service reste sur le réseau
     interne, comme
     backend et frontend. Seul le proxy publie. En développement,
     docker-compose.dev.yml
     publie 127.0.0.1:21632:5432 — jamais 0.0.0.0, qui exposerait la base à tout
     le réseau
     local, et pas 5432, qui entrerait en collision avec un Postgres installé
     sur l'hôte.

     DATABASE_URL diffère donc entre les deux contextes : db:5432 (nom de
     service, réseau
     interne) en conteneur, 127.0.0.1:21632 depuis pnpm dev. C'est .env qui
     porte la
     différence, et .env.example doit montrer les deux formes en commentaire.

     Hors périmètre A1 mais à noter : docker-compose.yml publie aujourd'hui
     8080:80, donc sur
     toutes les interfaces et hors plage. Ce sera à corriger en
     127.0.0.1:21600:80 avec A5/A6.

     5. Volume nommé pgdata. docker compose down sans -v doit préserver les
     données ;
     c'est le comportement attendu et ça doit être vérifié, pas supposé.

     6. app.enableShutdownHooks(). Sans lui, Nest n'appelle jamais
     OnModuleDestroy sur
     SIGTERM : le $disconnect() de Prisma ne s'exécute pas et les connexions
     restent ouvertes
     côté Postgres jusqu'au timeout. C'est une dette identifiée depuis deux
     sessions (documentée
     dans ai-plans/2026-08-06-lint-backend-bloquant.md) ; elle devient réelle
     ici, puisqu'il y a
     enfin quelque chose à fermer proprement.

     7. Le lint est bloquant, et le client généré est du code qu'on n'écrit pas.
     Il doit
     figurer dans les ignores d'eslint.config.mjs, sinon --max-warnings 0 échoue
     sur des
     milliers de lignes générées. À faire par une entrée ignores ciblée, pas en
     désactivant des
     règles.

     Variables d'environnement

     Ajoutées à .env.example (valeurs vides) :

     POSTGRES_USER=
     POSTGRES_PASSWORD=
     POSTGRES_DB=
     DATABASE_URL=

     DATABASE_URL est la seule que lit l'application ; les trois autres ne
     servent qu'à
     l'initialisation du conteneur Postgres. Validation au démarrage : absente
     ou non conforme à
     postgresql://…, l'API refuse de démarrer avec un message nommant la
     variable. Ce contrôle
     se branche sur le .catch(...) déjà posé dans main.ts (message explicite,
     exit 1). A4
     généralisera le principe à tout le périmètre.
