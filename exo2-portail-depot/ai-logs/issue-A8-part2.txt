● Je réponds à la question de fond, puis j'écris le plan.

  Pourquoi les deux tests coexistent. Le déploiement de staging et ./install.sh
  prouvent deux choses différentes. Le sous-domaine prouve que cette instance-là
  tourne, avec son certificat. install.sh prouve que le dépôt est complet et 
  reproductible : que n'importe qui repart de zéro, qu'aucun secret n'a été
  recopié à la main sur le serveur, qu'aucune étape ne vit dans la tête de la
  personne qui a déployé. C'est la différence entre « ça marche chez toi » et «
  ça se réinstalle ». Un correcteur qui ne testerait que l'URL déployée ne
  saurait pas distinguer un projet livrable d'un projet bricolé en SSH.

  Donc oui, ils le lancent sur une machine à eux — avec un navigateur dessus.
  127.0.0.1:21600 y est la bonne adresse.

  Je tranche sur le cas SSH : je l'inclus. Dix lignes, qui ne s'affichent que si
  $SSH_CONNECTION est défini et DOMAIN vide. Ce n'est pas une instruction de
  réparation à aller chercher dans le README — c'est la bannière du script qui,
  dans le seul cas où l'URL qu'elle donne ne répondrait pas, dit pourquoi et
  donne la commande. Cas peu probable, coût quasi nul, et sans lui l'évaluateur
  voit une URL morte sans explication.

  1. Quand la connexion vient-elle « du réseau » ?

  Presque toujours. La zone trust se réduit à un seul endroit : l'intérieur du
  conteneur db.

  ┌────────────────────────┬─────────────────┬───────────────┬─────────────┐
  │          D'où          │ Adresse vue par │    Règle      │   Mot de    │
  │                        │     Postgres    │   appliquée   │ passe faux  │
  ├────────────────────────┼─────────────────┼───────────────┼─────────────┤
  │ conteneur backend → db │ 172.19.0.5      │ scram-sha-256 │ refusé      │
  ├────────────────────────┼─────────────────┼───────────────┼─────────────┤
  │ la machine (pnpm dev)  │ 172.17.0.1      │ scram-sha-256 │ refusé      │
  │ → port publié 21632    │                 │               │             │
  ├────────────────────────┼─────────────────┼───────────────┼─────────────┤
  │ docker compose exec db │ (vide, socket   │ trust         │ accepté     │
  │  psql                  │ locale)         │               │             │
  ├────────────────────────┼─────────────────┼───────────────┼─────────────┤
  │ docker compose exec db │ 127.0.0.1       │ trust         │ accepté     │
  │  psql -h 127.0.0.1     │                 │               │             │
  └────────────────────────┴─────────────────┴───────────────┴─────────────┘

  Le point surprenant est la deuxième ligne. On se connecte à 127.0.0.1:21632
  depuis la machine, mais Postgres ne voit pas 127.0.0.1 : la publication de
  port de Docker fait de la traduction d'adresse, donc la connexion se présente
  avec l'adresse de la passerelle du pont Docker, 172.17.0.1. La règle host all 
  all 127.0.0.1/32 trust ne s'applique donc pas. Autrement dit, pnpm dev
  s'authentifie pour de vrai — c'est une bonne nouvelle, et ce n'était pas
  évident.

  Et c'est là qu'est le piège : le seul endroit où trust s'applique est
  exactement celui où l'on va naturellement quand on débugue, parce que docker 
  compose exec db psql est la commande la plus courte à taper.

  2. Quand teste-t-on un mot de passe ?

  - diagnostiquer un échec d'authentification — ce qui est arrivé : le backend

  - après avoir fait tourner un secret, pour confirmer que le changement a bien
  pris ;
  - avant un déploiement, pour vérifier qu'un .env correspond à un volume

  Ce qu'il faut vraiment en retenir

  La règle n'est pas sur les mots de passe, elle est plus large : tester par le 
  même chemin que le vrai client. Un chemin de test plus permissif que le chemin
  réel ne prouve rien, et il ment dans le sens le plus dangereux — il vous
  rassure.
