● Le plan est écrit. En résumé de ce qu'A7 demande, puisque c'était le flou :

  Le proxy de la machine ne fait pas le HTTPS pour toi. En HTTP il lit le Host
  et te relaie sur 21600 ; en HTTPS il lit seulement le SNI dans le ClientHello,
  ouvre un tube vers 21601 et recopie les octets sans rien déchiffrer.
  Certificat, clé privée, négociation TLS : tout est chez toi. Ton nginx
  n'écoute aujourd'hui que sur :80, donc l'URL HTTPS ne répond pas du tout.

  Il faut donc trois choses : écouter aussi sur 127.0.0.1:21601 en TLS, obtenir 
  un certificat Let's Encrypt en publiant le jeton du challenge HTTP-01 sur
  /.well-known/acme-challenge/ (Let's Encrypt vient le lire par le :80 de la
  machine, qui te le relaie), et automatiser le renouvellement — un certificat
  vit 90 jours, sans quoi le portail casse dans trois mois. Le passage par
  l'endpoint staging d'abord n'est pas une politesse : la production plafonne à
  5 certificats identiques par semaine, donc quatre essais ratés grillent le
  domaine pour une semaine.

  Le plan retient un calque infra/docker-compose.tls.yml (le compose de base
  reste HTTP pur pour le correcteur, qui n'a pas de domaine public), certbot en
  webroot, et un sidecar de renouvellement — avec, au passage, une découverte à
  consigner : en passthrough SNI, $remote_addr est l'IP du proxy frontal et non
  celle du client, ce dont G1 (rate limiting par IP) ne pourra pas se servir.

  Sources : Let's Encrypt — challenge types, rate limits, Certbot user guide,
  Mozilla SSL Config Generator, Compose merge, renouvellement automatique 
  nginx+certbot.

  1. Le sidecar et le dry-run. Non, le sidecar ne fait pas de dry-run : il lance
  le vrai certbot renew toutes les 12 h. C'est sans danger et sans quota, parce
  que renew est un no-op tant qu'il reste plus de 30 jours — il regarde la date
  d'expiration et ne sort qu'à ce moment-là. Le --dry-run est une vérification
  manuelle et ponctuelle : il rejoue tout le protocole contre l'endpoint de test
  pour prouver que le mécanisme marchera le jour venu, sans toucher au
  certificat réel. C'est précisément la case « renouvellement automatique
  vérifié (dry-run) » du backlog : on ne peut pas attendre 60 jours pour savoir.

  2. DOMAIN. Dans le plan initial il ne servait qu'à deux choses : certbot -d 
  $DOMAIN (quel nom demander) et la vérification curl --resolve. nginx, lui,
  n'en a pas besoin — d'où le --cert-name portail. Mais ta remarque sur --tls me
  fait lui donner un meilleur rôle, voir plus bas.

  3. Les templates nginx. L'image officielle sait substituer des variables
  d'environnement dans une conf : tu déposes
  /etc/nginx/templates/x.conf.template, et son entrypoint fabrique
  /etc/nginx/conf.d/x.conf en remplaçant ${DOMAIN}. Sauf que ce mécanisme vit
  dans les scripts /docker-entrypoint.d/*.sh, que l'entrypoint n'exécute que si 
  la commande qu'on lui demande de lancer est nginx. Notre boucle de
  rechargement remplace la commande par sh -c '…' : les scripts sont sautés,
  aucune substitution n'a lieu, et un ${DOMAIN} resterait littéral dans la conf.
  C'est pour ça que le nom du domaine ne doit apparaître nulle part côté nginx
  — la lignée de certificat s'appelle portail, un nom fixe.

  4. Pas de scp. Tu te connectes en SSH et tu clones : git clone 
  --filter=blob:none --sparse + git sparse-checkout set sur infra/,
  .env.example, install.sh. La recette est déjà dans infra/README.md. Un scp -r 
  infra marcherait mais perd la traçabilité de version — impossible de dire quel
  commit tourne.

  5. « Servi dans les deux modes ». C'est le problème de l'œuf et de la poule :
  nginx refuse de démarrer si ssl_certificate pointe sur un fichier absent. Donc

  6. Oui, le calque = surcharges du proxy (port 21601, conf TLS, sonde HTTPS,

● Vite fait, les deux notions :

  location, c'est du nginx. À l'intérieur d'un server { }, un location dit «
  pour les URL qui ressemblent à ça, fais ceci ». nginx choisit un seul location
  par requête, le plus spécifique. Les nôtres, aujourd'hui :

  location = /api/v1/health { deny all; }        # exactement cette URL   -> 
  refusée
  location /api/          { proxy_pass ...:21610; }  # tout ce qui commence par 
  /api/ -> le backend
  location /              { proxy_pass ...:3000; }   # tout le reste      -> le 
  frontend

  Le = est une correspondance exacte, évaluée avant les préfixes — c'est ce qui
  fait que /api/v1/health est bloqué alors qu'il commencerait aussi par /api/.
  A7 en ajoute un quatrième, pour le challenge :

  location /.well-known/acme-challenge/ { root /var/www/certbot; }

  Celui-là ne proxy rien : il sert des fichiers du disque, pris dans
  /var/www/certbot.

  webroot, c'est la méthode de certbot qui exploite exactement ça. Il y a
  plusieurs façons de prouver à Let's Encrypt qu'on possède le domaine ;
  --webroot est celle qui ne touche à rien :

  1. certbot écrit le fichier-jeton dans le répertoire qu'on lui donne (-w 
  /var/www/certbot) ;
  2. Let's Encrypt appelle http://ton-domaine/.well-known/acme-challenge/<jeton>
  ;
  3. nginx, déjà en marche, sert ce fichier grâce au location ci-dessus ;
  4. certbot récupère le certificat et efface le jeton.

  C'est pour ça que certbot et nginx partagent le volume certbot_www : l'un
  écrit dedans, l'autre le lit. L'alternative, --standalone, ferait tourner un
  serveur web à certbot lui-même sur le port 80 — impossible ici, nginx
  l'occupe, et il faudrait l'arrêter le temps de l'opération (donc une coupure à
  chaque renouvellement).

● Oui, nginx est le reverse proxy. C'est le seul point d'entrée de ton portail :
  il reçoit toutes les requêtes et les répartit — /api/... vers le backend
  NestJS, tout le reste vers le frontend React. C'est aussi lui qui refuse
  l'accès à la sonde de santé, qui limite la taille des fichiers déposés, et
  maintenant qui déchiffre le HTTPS. « Reverse » (inverse) parce qu'il
  représente tes serveurs face aux visiteurs, alors qu'un proxy ordinaire
  représente un visiteur face à internet.

  Il y a deux proxies empilés, et c'est la source de confusion habituelle :

  visiteur ──► proxy de la machine partagée ──► TON nginx ──► backend / frontend
               (trie les candidats par nom)     (le reverse proxy du portail)

  Le proxy de la machine ne fait que du tri : il regarde à qui la requête est
  destinée et te la transmet sur ton port. En HTTPS il ne l'ouvre même pas — il
  recopie les octets chiffrés. C'est pour ça que le déchiffrement t'incombe.

  ────────────────────────────────────────
  Option: certonly

  Option: --webroot -w /var/www/certbot

  Ce qui marche, et que j'ai vérifié moi-même. Le portail répond en HTTPS sur

  jusqu'à une autorité reconnue — donc que les navigateurs l'accepteront aussi.
  Le HTTP redirige, la sonde de santé reste inaccessible, et le routage /api/
  atteint bien le backend.

  Le contrôle qui comptait le plus. Aucun des six ports du projet n'accepte de
  connexion depuis internet. La machine est partagée avec d'autres candidats :
  un seul port ouvert au mauvais endroit aurait exposé la base de données par
  /api et la console de stockage, c'est-à-dire les pièces confidentielles des
  clients.

  Ce que j'ai écrit. Le backlog et le plan daté portent maintenant les résultats
  mesurés, pas des intentions. Commit e379f64, pas encore poussé.

  Ce qui manque pour clore A7 — une seule chose. Le renew --dry-run. Il rejoue
  tout le protocole de renouvellement contre le serveur de test, sans toucher au
  vrai certificat, et c'est le seul moyen de savoir aujourd'hui que le
  renouvellement fonctionnera dans deux mois. Sans lui, tu découvrirais un
  problème le jour où le portail cesserait de répondre. Sur la machine :

  cd technical-interview/exo2-portail-depot
