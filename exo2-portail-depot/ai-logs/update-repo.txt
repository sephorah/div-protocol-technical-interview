● Oui, ./install.sh marche et il est fait pour être rejoué — mais ce n'est pas
  le chemin le plus court, et sur une machine de dev il y a un piège.

  Le piège : ./install.sh tire les images publiées, il ne construit pas ton
  arbre de travail. Sur la machine de dev, il déploie donc ce qui est sur GHCR —
  pas tes modifications locales non commitées. Pour déployer ton code local,
  c'est ./install.sh --from-source.

  Les trois chemins :

  ┌─────────────────────────────────────────────┬───────────────────────────┐
  │               Ce que tu veux                │        La commande        │
  ├─────────────────────────────────────────────┼───────────────────────────┤
  │ Redéployer la version publiée (le cas       │ pnpm stack:pull && pnpm   │
  │ courant)                                    │ stack:up                  │
  ├─────────────────────────────────────────────┼───────────────────────────┤
  │ Déployer ton code local non publié          │ ./install.sh              │
  │                                             │ --from-source             │
  ├─────────────────────────────────────────────┼───────────────────────────┤
  │ Repartir de zéro, ou revalider le parcours  │ ./install.sh              │
  │ des correcteurs                             │                           │
  └─────────────────────────────────────────────┴───────────────────────────┘

  Ce qu'install.sh fait en plus de stack:pull && stack:up : il complète .env
  avec les clés qu'.env.example a gagnées, vérifie le port 21600, attend chaque
  healthcheck, rejoue le seed, et imprime les URLs et les identifiants.

  Et c'est le seed qui compte pour un redéploiement. src/seed.ts appelle
  regenerate : il révoque le lien de démonstration et en crée un nouveau, à
  chaque exécution. Le PIN étant haché, l'ancien ne peut pas être réaffiché —
  donc un lien déjà envoyé cesse de fonctionner et un nouveau PIN est imprimé.
  C'est voulu (un lien de démo dont personne ne connaît le PIN ne vaut rien),
  mais ça fait d'install.sh un mauvais outil pour un simple redéploiement si tu
  as partagé le lien.

  install.sh est idempotent par ailleurs : les secrets ne sont jamais régénérés
  (set_env_default ne remplit que le vide), et le port tenu par notre propre
  proxy n'est pas vu comme un conflit — un second ./install.sh ne échoue pas
  contre lui-même.

  Dans ton cas immédiat — la pile tourne en 0.4.0, 0.4.1 est publiée et le
  compose l'épingle par défaut — c'est pnpm stack:pull && pnpm stack:up. Je le
  lance ?
