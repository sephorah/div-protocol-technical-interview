● Le dépôt sephorah/technical-interview est public — ça tranche une des
  questions. Réponses, puis plan mis à jour.

  1. Le repli sur build : tu as raison, je le retire. Il ne servait que sur la
  machine de l'évaluateur qui, elle, n'aura pas de sources. Sur un checkout
  config-only, backend/ n'existe pas : le repli ne se déclencherait jamais et
  masquerait juste la vraie cause. Pull KO ⇒ le script s'arrête en nommant les
  trois causes possibles. Je garde --from-source comme drapeau explicite (le
  calque docker-compose.build.yml), pour une seule raison : pouvoir vérifier la
  stack de production en local avant de publier quoi que ce soit.

  2. GHCR vs Docker Hub — oui, et pour trois raisons, dont une décisive ici.
  Authentification : GITHUB_TOKEN est injecté dans le workflow, GHCR l'accepte
  tel quel ; Docker Hub demande de créer un compte, un access token, et de le
  déposer en secret de dépôt — un secret de plus à gérer et à faire tourner.
  Permissions : sur GHCR elles sont celles du dépôt (packages: write dans le
  workflow), sur Docker Hub c'est un système d'organisations séparé. Et surtout
  le rate limit : Docker Hub plafonne les pulls anonymes à 100 par 6 h par 
  adresse IP — or la machine de staging est partagée avec d'autres candidats,
  donc l'IP aussi. GHCR n'applique aucune limite sur les paquets publics.
  Sources : Docker Hub rate limits (OSC), GitLab, mars 2025, Working with the 
  Container registry.

  3. Exposer le dist/ compilé : la question ne se pose plus. gh repo view dit
  "visibility":"PUBLIC" — le TypeScript source est déjà lisible par tout le
  monde sur GitHub. Une image publique n'ajoute donc rien, elle en révèle même
  moins. Ce qui compte réellement, et qui reste vrai dans les deux cas : aucun
  secret ne doit être cuit dans une couche — une couche est immuable et reste
  tirable même après suppression du tag. Ici la configuration arrive à
  l'exécution par l'environnement, et .env n'entre pas dans le contexte de build
  (les contextes sont backend/ et frontend/, .env est à la racine). C'est ça
  que je vérifie avant le premier push, pas l'obfuscation.

  4. « Chaîne d'approvisionnement descendante », en clair : un tag est un
  post-it, pas le contenu. Rien n'empêche de repousser 1.2.0 avec une image
  différente ; la prod qui fait pull récupère alors autre chose sans qu'une
  ligne de compose ait bougé. Le seul identifiant qui désigne un contenu est le
  digest (image: …@sha256:…). Je ne l'utilise pas parce qu'il faut réécrire le
  compose à chaque release — c'est un arbitrage, pas un oubli, et il va dans les
  limites connues. GitHub propose bien une immutabilité de tags, mais elle est
  native pour les Actions publiées en OCI, pas pour un paquet conteneur
  ordinaire (publish-immutable-action).

  5. Comment publie-t-on sur GHCR, concrètement : le workflow se connecte à
  ghcr.io avec le GITHUB_TOKEN que GitHub fabrique pour ce run
  (docker/login-action, user ${{ github.actor }}), à condition que le job
  déclare permissions: packages: write. Il construit et pousse vers
  ghcr.io/<owner>/<nom>:<tag>. Le paquet naît privé : il faut le passer en
  public une fois, dans ses Settings, sinon le docker pull anonyme répond 403 —
  indiscernable d'une image inexistante. Le label
  org.opencontainers.image.source (posé par docker/metadata-action) est ce qui
  rattache le paquet au dépôt. Aucun PAT, ni en CI ni sur la machine.

● Vérifié — deux réponses.

  --from-source, le problème d'amorçage. Le compose de production ne contient
  plus aucun build: : la première fois qu'on l'exécute, il tire une image qui
  n'existe pas encore. On ne peut donc le tester qu'après avoir publié —
  c'est-à-dire tester en production ce qu'on n'a jamais vu marcher. Le calque
  résout ça : il construit les images en les taguant sous leur nom GHCR, et
  docker n'allant pas chercher au registre ce qu'il a déjà en local, docker 
  compose -f infra/docker-compose.yml up seul remonte alors toute la stack hors
  ligne. Ce que ça attrape avant le push : un nom d'image faux, une variable
  perdue en retirant la section build, un montage cassé. C'est aussi le seul
  moyen de vérifier localement une correction d'image sans repasser par un tag
  git. Note qu'un pnpm stack:build fait la même chose : le drapeau dans
  install.sh existe pour la machine qui n'a ni Node ni pnpm.

  Le passage en public : non automatisable depuis le workflow, mais évitable. Il
  n'existe aucun endpoint REST pour changer la visibilité d'un paquet
  conteneur, et l'héritage n'a pas lieu — la doc est explicite : « a package
  automatically inherits the access permissions (but not the visibility) of the
  linked repository », et « when you first publish a package scoped to your
  personal account, the default visibility is private ». En revanche il y a un
  réglage de compte : Settings → Packages → Package creation → default 
  visibility. Mis à Public avant le premier push, les deux paquets naissent
  publics et il n'y a plus rien à faire après. C'est mieux que corriger après
  coup : ça supprime la fenêtre où le paquet existe, est privé, et fait échouer
  un déploiement en 403. Attention, l'opération est à sens unique — public ne
  redevient jamais privé.

  Sources : Configuring a package's access control and visibility, Working with 
  the Container registry, GH Actions & GHCR package visibility.

     │ Comment la publication fonctionne                                       │
     │                                                                         │
     │ 1. Le workflow déclare permissions: { contents: read, packages: write   │
     │ }. GitHub fabrique alors un                                             │
     │ GITHUB_TOKEN éphémère portant ce droit, propre au run.                  │
     │ 2. docker/login-action s'authentifie sur ghcr.io avec ${{ github.actor  │
     │ }} et ce token. Aucun                                                   │
     │ PAT n'est créé, ni en CI ni sur la machine de production.               │
     │ 3. docker/build-push-action pousse vers                                 │
     │ ghcr.io/sephorah/exo2-portail-depot-{backend,frontend}.                 │
     │ 4. Le paquet est privé à sa création : un docker pull anonyme répond    │
     │ alors 403, symptôme                                                     │
     │ indiscernable d'un tag inexistant. Aucun endpoint REST ne change cette  │
     │ visibilité, et le paquet                                                │
     │ hérite des permissions du dépôt mais pas de sa visibilité. Il faut donc │
     │ passer ces deux                                                         │
     │ paquets en Public dans leurs Settings, une fois, après le premier push. │

     │ (Package creation → default visibility) le ferait automatiquement mais  │
     │ vaudrait pour tous les                                                  │
     │ futurs paquets du compte, y compris ceux de dépôts privés : écarté      │
     │ délibérément. Étape manuelle,                                           │
     │ à écrire dans infra/README.md.                                          │

     │ docker/metadata-action) rattache le paquet                              │

     │ Sécurité                                                                │
     │                                                                         │
     │ - Le dépôt est public. Les sources TypeScript sont déjà lisibles de     │
     │ tous : une image publique                                               │
     │ n'ajoute aucune exposition, elle en révèle même moins que le dépôt. Le  │
     │ débat « faut-il cacher le                                               │
     │ dist/ » n'a pas lieu d'être ici, et l'obscurité n'a jamais été un       │
     │ contrôle de sécurité.                                                   │
     │ - Le vrai risque est le secret cuit dans une couche. Une couche est     │
     │ immuable et reste tirable                                               │
     │ après suppression du tag. Ici la configuration arrive à l'exécution par │
     │ l'environnement et .env                                                 │
     │ vit à la racine, hors des contextes de build (backend/, frontend/) — à  │
     │ reconfirmer par                                                         │
     │ inspection de l'image avant le premier push, l'opération étant          │
     │ irréversible en pratique                                                │
     │ (miroirs, caches).                                                      │
     │ - packages: write sur le seul job de publication, contents: read au     │
     │ niveau du workflow,                                                     │
     │ aucun déclencheur pull_request.                                         │
     │ - Actions épinglées au SHA : sans cela, la compromission d'un tag amont │
     │ donne un accès en                                                       │
     │ écriture au registre.                                                   │
     │ - Un tag n'identifie pas un contenu. C'est un post-it : rien n'empêche  │
     │ de repousser 0.1.0 avec                                                 │
     │ une image différente, et la production qui fait pull récupère autre     │
     │ chose sans qu'une ligne de                                              │
     │ compose ait bougé. Seul le digest (image: …@sha256:…) désigne un        │
     │ contenu. Il n'est pas retenu                                            │
     │ parce qu'il impose de réécrire le compose à chaque release ; c'est un   │
     │ arbitrage assumé, à inscrire                                            │
     │ dans les limites connues, avec la signature cosign. L'immutabilité      │
     │ native de GitHub couvre les                                             │
     │ Actions publiées en OCI, pas un paquet conteneur ordinaire              │
     │ (publish-immutable-action).                                             │
     │ - Aucun credential de registre sur la machine partagée — c'est ce que   │
     │ la visibilité publique                                                  │
     │ achète, et c'était la raison principale de la préférer.                 │
     │ - Risque résiduel : l'image publique expose l'arbre des dépendances,    │
     │ donc les CVE applicables,                                               │
     │ à qui la tire. Le dépôt public l'exposait déjà via les lockfiles.       │

● La pratique établie, c'est les deux à la fois, et elles ne servent pas au même
  moment.

  1. Compose de base = production, calque pour construire. C'est le motif
  documenté de Compose : un fichier de base qui décrit la production, des
  fichiers d'override fusionnés dans l'ordre des -f pour les besoins locaux — le
  build depuis les sources en étant l'usage typique. Rien d'exotique donc, et
  une seule description de la stack. Une nuance sur le nom : j'évite
  docker-compose.override.yml, que Compose charge automatiquement quand il est
  là — un fichier magique qui construirait en local alors qu'on croit tirer.
  docker-compose.build.yml, explicitement passé en -f, ne s'applique que si on
  le demande. (Compose : plusieurs fichiers, override files)

  2. « Build once, run anywhere » — ce qu'on teste doit être ce qu'on déploie.
  C'est le principe build, release, run des 12 facteurs, et il dit qu'une image
  reconstruite localement n'est pas l'artefact : même Dockerfile, mais un autre
  moment, un autre cache, un autre index de paquets. La forme forte de la
  vérification est donc de faire construire par le CI, puis de tirer cette 
  image-là et de la lancer avec le compose de production :

  IMAGE_TAG=sha-abc1234 docker compose -f infra/docker-compose.yml --env-file
  .env up -d

  C'est précisément pourquoi le workflow publie un tag sha-<court> sur chaque
  push de main, en plus des tags semver : ça donne un artefact vérifiable avant
  de promouvoir une version.

  Les deux se complètent : le calque attrape en dix secondes et hors ligne les
  erreurs de compose (nom d'image, variable perdue, montage cassé) ; le tag sha-
  est la porte avant de poser exo2-v0.1.0. Je garde donc --from-source, et
  j'ajoute l'étape « tirer le sha- et le faire tourner avant de tagger » à la
  vérification.

● Les trois familles de tags, produites automatiquement :

  À quoi il sert: désigne un commit précis, ne bouge jamais. C'est ce qu'on
