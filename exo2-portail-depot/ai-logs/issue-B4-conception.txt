● B3 — Lien public expirable protégé par PIN (fait, fusionné dans main)

  C'est la dernière issue métier livrée. Elle a rendu le lien de dépôt
  réellement utilisable et réellement expirable — avant elle, expiresAt était
  écrit à la création et lu par personne.

  Ce qui a été construit

  - PUBLIC_BASE_URL — l'origine à partir de laquelle l'URL client est composée,
  requise et validée au démarrage (origine nue : ni chemin ni paramètres).
  Jamais l'en-tête Host, qui est fourni par l'appelant : un appel forgé ferait
  renvoyer un lien vers le domaine d'un attaquant, que l'avocat collerait
  ensuite dans un courriel. install.sh la réaligne sur https://$DOMAIN quand
  HTTPS s'active.
  - La réponse de création porte l'URL complète (IssuedLink.url), plus le jeton
  nu — le jeton n'avait pas de consommateur propre, l'adresse est ce qu'on
  copie.
  - PublicLinksService (src/requests/public-links.service.ts) avec trois
  opérations : resolve (la brique sur laquelle C1 se branchera, applique
  révocation puis expiration), regenerate, revoke.
  - Deux routes avocat : POST /requests/:id/link régénère (révoque l'actif, émet
  jeton + PIN + échéance neufs), DELETE /requests/:id/link coupe sans
  réémettre, idempotent, 204.
  - Masquage du jeton côté nginx : Referrer-Policy: no-referrer, X-Robots-Tag: 
  noindex, et un map qui réécrit le segment du jeton en [redacted] dans les
  journaux — la machine est partagée avec d'autres candidats. Le -L de serve a
  été retiré dans frontend/Dockerfile pour la même raison.

  Les arbitrages qui ne sont pas dans l'énoncé

  - Régénérer, pas prolonger. Prolonger rallonge la vie d'un jeton déjà parti
  par courriel, hors de tout contrôle. Ce qui justifie la route n'est pas le
  client qui égare son PIN, c'est l'avocat qui ne l'a jamais vu : le PIN
  n'apparaît qu'une fois, en argon2id en base — un onglet fermé et la demande
  est valide sans que personne n'en connaisse le code.
  - 404, pas 403, sur une demande appartenant à un autre avocat — un 403
  confirme qu'un identifiant existe et suffit à énumérer les dossiers d'un
  confrère.
  - Jeton dans le chemin, pas après un #. La parade radicale (jamais envoyé au
  serveur) imposerait le jeton dans le corps, donc une surface d'API qui
  s'écarte de la consigne. D'où les deux mitigations nginx ci-dessus.

  Vérifié : 246 tests unitaires, 61 e2e, lint sans avertissement ; régénération
  en 201 à travers nginx en 97 ms, une seule ligne PublicLink active par
  demande, [redacted] confirmé dans le journal du proxy. Campagne machine vierge

❯ Pourquoi il faudrait un téléchargement des pièces?                            

● Parce que sans lui le portail collecte des pièces que personne ne peut lire.
  Le but du produit, c'est la première phrase de l'énoncé : « un avocat monte un
  dossier et doit récupérer des pièces chez son client ». Aujourd'hui ça se
  passe par mail — et par mail, l'avocat a le fichier. Si le portail remplace ça
  sans jamais rendre les fichiers, il fait moins bien que ce qu'il remplace :
  les pièces partent chez MinIO et y restent.

  Deux nuances, parce que la question est légitime :

  - Ce n'est pas dans la liste de routes de l'énoncé. Elle s'arrête à POST 
  /public/:token/files. Ce que l'énoncé montre en revanche, côté maquette
  avocat, c'est « une ligne par pièce, action à droite » — l'action n'est pas
  nommée, mais sur une pièce reçue il n'y en a guère d'autre que la consulter.
  - C'est le backlog qui en a fait un critère de B4, pas la consigne. Et c'est
  justement pourquoi on vient de le sortir : tant que C2 n'existe pas, il n'y a
  rien à télécharger, et la route serait livrée sans qu'aucun chemin réel ne
  l'ait exercée. Elle demande en plus des décisions qui appartiennent à C2 — URL
  présignée MinIO ou flux à travers l'API, Content-Disposition, durée de
  validité du lien de téléchargement.

  Donc : nécessaire au produit, oui ; nécessaire à cette issue, non.

  Je reprends le cadrage.

  1. Surface de l'API

  Deux routes, toutes deux sous le garde global (aucun @Public()), dans le
  RequestsController existant.

  GET /requests?page=1&pageSize=20

  {
    "items": [
      {
        "id": "…", "title": "Dossier Martin, pièces 2026",
        "createdAt": "2026-08-09T10:12:03.114Z",
        "status": "pending",
        "expectedCount": 3,
        "receivedCount": 1,
        "link": { "state": "active", "expiresAt": "2026-09-08T10:12:03.114Z" }
      }
    ],
    "page": 1, "pageSize": 20, "total": 47, "totalPages": 3
  }

  Trié du plus récent au plus ancien. pageSize borné à 100 — un dashboard n'en a
  pas besoin de plus, et la borne empêche un appelant authentifié de demander
  la table entière en une requête.

  GET /requests/:id — le même objet, plus les pièces :

  {
    "…": "les champs ci-dessus",
    "items": [
      { "id": "…", "label": "Bail", "received": true,
        "file": { "originalName": "bail.pdf", "mimeType": "application/pdf",
                  "sizeBytes": 184320, "receivedAt": "2026-08-09T14:02:11.007Z"
  } },
      { "id": "…", "label": "Pièce d'identité", "received": false, "file": null
  }
    ]
  }

  Les pièces sortent dans l'ordre position, jamais createdAt — elles partagent
  leur horodatage à la milliseconde (contrainte posée par B2).

  Trois points qui se décident ici, pas à l'implémentation :

  - Le statut se calcule sur le dernier lien émis, actif ou non. Une demande
  dont le lien est révoqué garde donc pending / complete / expired, et c'est
  link.state qui dit que plus personne ne peut déposer. Les deux faits sont
  indépendants : une demande peut être complète et coupée.
  - Une demande qui n'appartient pas à l'appelant répond 404, pas 403 — la règle
  que B3 a déjà posée, pour la même raison : un 403 confirme qu'un identifiant
  existe chez un autre avocat.
  - Aucune donnée de lien secrète ne sort : ni jeton, ni PIN, ni hachage. Le
  dashboard n'a besoin que de l'échéance et de l'état. Le jeton n'existe en
  clair qu'à la création et à la régénération, et cette issue ne doit pas
  rouvrir cette porte.

  Est-ce que cette surface te va avant que je passe à la mise en œuvre et aux
  tests ?

● Deux réponses d'abord.

  link — j'avais mis trois valeurs, c'est une de trop. expiresAt est toujours là
  : il vient de la dernière ligne PublicLink émise, qui survit à sa révocation
  (B3 révoque en datant revokedAt, il ne supprime rien). Donc state: 'active' | 
  'revoked' avec son expiresAt dans les deux cas. Je garde revoked plutôt
  qu'inactive parce que les deux façons de ne plus être utilisable n'appellent
  pas la même action : un lien expiré et un lien révoqué se distinguent déjà par
  status: expired, et l'avocat qui a coupé lui-même veut savoir que c'est sa
  décision qu'il voit. Le seul cas où link serait absent, c'est une demande sans
  aucun lien — impossible aujourd'hui, la création les écrit dans la même
  transaction — donc link: LinkView | null et le compilateur oblige à traiter le
  cas plutôt qu'à inventer une date.

  GET /requests/:id — oui, exactement : le détail d'une demande précise. Ses
  pièces attendues, lesquelles sont arrivées, et quand. La liste ne porte que
  les compteurs (1 sur 3), pas les libellés.

● Trois réponses, dont une qui change le plan.

  1. Le lien nullable — tu as raison, il ne devrait pas l'être. Je m'étais
  protégé contre un cas qui ne peut pas arriver : la création écrit la demande
  et son lien dans la même transaction, la révocation date revokedAt sans rien
  supprimer, la régénération révoque puis insère. Une demande a donc toujours au
  moins un lien. Rendre le champ nullable, c'était payer un | null que tout
  appelant doit traiter, pour couvrir une ligne que seule une corruption de la
  base peut produire — et, pire, la masquer : la demande serait rendue
  normalement, avec link: null, et personne ne verrait le problème. Je supprime
  la tâche 1 (deriveStatus ne bouge plus du tout) et je traite le cas là où il
  appartient : si la liste des liens est vide, c'est un invariant cassé, on lève
  une erreur nommée qui se voit dans les journaux.

  2. Le statut dérivé — oui, mais la raison est plus dure qu'un coût de mise à 
  jour. Une colonne ne serait pas seulement pénible à tenir à jour, elle serait
  fausse. « Expirée » dépend de l'horloge : entre l'instant d'expiration et le
  passage du job qui bascule la colonne, la base affirme « en attente » sur une
  demande que plus personne ne peut ouvrir. Et sans job, elle le dit pour
  toujours. Ici la dérivation ne coûte rien de plus : les pièces et l'échéance
  sont déjà chargées par la même requête. C'est la décision qu'A2 avait
  consignée, B4 ne fait que la consommer.

  3. pageSize — la constante existe déjà côté DTO (MAX_PAGE_SIZE = 100,

     Context

     L'avocat peut créer une demande (B2) et gérer son lien (B3), mais il ne 
     peut rien relire.
     POST /requests répond une fois, et ensuite la demande disparaît de sa vue :
     aucune route ne dit
     quelles demandes existent, laquelle a reçu ses pièces, laquelle a expiré.
     L'énoncé fige pourtant
     GET /requests — « Affiche le tableau de bord avec listes et statuts » — et
     décrit le produit par
     ce dashboard : « Un dashboard lui montre le statut de chaque demande : en
     attente, complète,
     expirée. »

     B4 livre les deux routes de lecture qui manquent, et rien d'autre. Le
     quatrième critère du
     backlog, « téléchargement des pièces déposées », sort du périmètre : C2 (le
     dépôt) n'existe pas, donc
     aucune ligne UploadedFile ne peut naître autrement qu'insérée à la main, et
     la route serait livrée
     sans qu'aucun chemin réel ne l'ait exercée. Elle demande en plus des
     décisions qui appartiennent à
     C2 — URL présignée MinIO ou flux à travers l'API, Content-Disposition,
     durée de validité. Elle
     devient une issue B4b, dépendante de C2.

     Goal: donner à l'avocat la liste paginée de ses demandes avec leur statut
     dérivé, et le détail
     d'une demande avec ses pièces attendues, reçues et horodatées.

     Architecture: deux routes de lecture ajoutées au RequestsController
     existant, servies par
     RequestsService. Le statut reste dérivé à la lecture par deriveStatus, la
     fonction pure que
     B2 a écrite pour ça, réutilisée sans modification. Une page = deux requêtes
     SQL dans une
     transaction (la page et son total), les compteurs de pièces venant du même
     select que les pièces.

     Tech Stack: NestJS 11, Prisma 7 (@prisma/adapter-pg), class-validator /
     class-transformer,
     Jest + supertest contre un vrai Postgres.

     - Tout le code en anglais — identifiants, commentaires, noms de tests.
     Seuls les messages
     destinés à l'avocat sont en français.
     - Chaque décorateur class-validator porte son message explicite, en
     français. Un test
     échoue si un message contient « must be » (motif posé par

     ---
     Décisions de conception

     Quatre choix sont arrêtés et ne se rediscutent pas à l'implémentation.

     1. Le statut garde les trois valeurs de l'énoncé ; l'état du lien est un 
     champ séparé.
     Une demande dont le lien a été révoqué (B3) n'a plus de lien actif, mais sa
     dernière ligne
     PublicLink survit avec son expiresAt — la révocation date revokedAt, elle
     ne supprime rien. Le
     statut se calcule donc sur le dernier lien émis, actif ou non, et
     link.state dit le reste. Les
     deux faits sont indépendants : une demande peut être complète et coupée, et
     un statut unique
     écraserait l'un des deux.

     2. Le statut reste dérivé, jamais stocké. Une colonne ne serait pas
     seulement pénible à tenir à
     jour, elle serait fausse : « expirée » dépend de l'horloge, donc entre
     l'instant d'expiration et
     le passage d'un hypothétique job, la base affirmerait « en attente » sur
     une demande que plus
     personne ne peut ouvrir. Ici la dérivation ne coûte rien : les pièces et
     l'échéance sont déjà
     chargées par la même requête.

     3. link n'est pas nullable, et une liste de liens vide lève une erreur. Une
     demande a toujours
     au moins un lien, par construction. Rendre le champ nullable ferait traiter
     à tout appelant un cas
     que seule une corruption de la base produit — et le masquerait, la demande
     étant alors rendue
     normalement avec link: null.

     4. Pas de filtre par statut. Le statut étant dérivé, le filtrer
     correctement veut dire le
     recalculer en SQL, donc en avoir deux définitions qui peuvent diverger sans
     qu'aucun test ne le
     voie. Ni l'énoncé ni le backlog ne le demandent.

     5. received reste « un fichier est attaché », comme B2. UploadedFile.status
     peut valoir
     failed (colonne prévue pour C4) ; compter un fichier refusé comme reçu sera
     faux. Ce n'est pas
     tranché ici parce que rien ne peut encore écrire failed : c'est un point
     ouvert consigné pour C2,
     pas une dette silencieuse.

     Sécurité

     - 404 et jamais 403 sur la demande d'un autre avocat : un 403 confirme
     qu'un identifiant existe
     chez un confrère, ce qui suffit à énumérer sa clientèle. La règle vient de
     B3, elle est réutilisée
     telle quelle.
     - Filtrage par lawyerId dans le where, jamais après coup. La liste et le
     détail passent tous
     deux par un where portant les deux critères, donc il n'existe aucune
     branche où l'appartenance
     peut être oubliée.
     - pageSize borné par MAX_PAGE_SIZE. Sans borne, un appelant authentifié
     demande la table
     entière et ses pièces en une requête.
     - Aucun hachage, aucun jeton, aucun PIN dans les réponses. Un test e2e
     balaie tout le corps et
     échoue si une clé contient hash, token ou pin.
     - Risques résiduels, à consigner au README : originalName est fourni par le
     client et ressorti
     tel quel — B5 devra l'échapper à l'affichage (il n'est jamais utilisé comme
     chemin, le schéma le
     dit déjà) ; et la pagination par décalage peut montrer deux fois ou sauter
     une demande si une
     création survient pendant qu'on feuillette.

     type LinkState = 'active' | 'revoked';
     interface LinkView { state: LinkState; expiresAt: Date }
     interface ReceivedFileView { originalName: string; mimeType: string;
     sizeBytes: number; receivedAt: Date }
     interface DetailedItemView { id: string; label: string; received: boolean;
     file: ReceivedFileView | null }
     interface RequestSummaryView {
       id: string; title: string; createdAt: Date;
       status: RequestStatus; expectedCount: number; receivedCount: number;
     link: LinkView;
     }

     /** The columns of the last link the queries select, and nothing more. */
     type LinkRow = { expiresAt: Date; revokedAt: Date | null };

     /** Only the presence of a file matters to a count. */
     type CountedItemRow = { file: unknown | null };

     type SummaryRow = {
       id: string;
       title: string;
       createdAt: Date;
       items: CountedItemRow[];
       links: LinkRow[];
     };

     type DetailRow = Omit<SummaryRow, 'items'> & {
       items: {
         id: string;
         label: string;
         file: {
           originalName: string;
           mimeType: string;
           sizeBytes: number;
           createdAt: Date;
         } | null;
       }[];
     };

     /**
      * A request ALWAYS has at least one link: creation writes both in one
      * transaction, revocation only dates revokedAt, and regeneration revokes 
     then
      * inserts. An empty list is therefore a broken invariant -- rows deleted 
     by
      * hand, or a future feature that deletes links -- and it belongs in the 
     logs,
      * not in a 200 whose `link` is quietly null.
      */
     const toLinkView = (links: LinkRow[], requestId: string): LinkView => {
       const [latest] = links;
       if (latest === undefined) {
         throw new Error(`La demande ${requestId} n'a aucun lien public.`);
       }
       return {
         state: latest.revokedAt === null ? 'active' : 'revoked',
         expiresAt: latest.expiresAt,
       };
     };

     const countReceived = (items: CountedItemRow[]): number =>
       items.filter((item) => item.file !== null).length;

     /**
      * Field by field, never a spread: it is then the compiler, and not the 
     author's
      * vigilance, that keeps pinHash and tokenHash out of a response when a 
     column
      * is added later. Same rule as toCreatedRequest.
      */
     export const toRequestSummary = (
       row: SummaryRow,
       now: Date,
     ): RequestSummaryView => {
       const link = toLinkView(row.links, row.id);
       const expectedCount = row.items.length;
       const receivedCount = countReceived(row.items);

       return {
         id: row.id,
         title: row.title,
         createdAt: row.createdAt,
         status: deriveStatus(
           {
             // The deadline of the LAST link, revoked or not: the status 
     describes
             // the file, and `link` describes access to it.
             expiresAt: link.expiresAt,
             expectedCount,
             receivedCount,
           },
           now,
         ),
         expectedCount,
         receivedCount,
         link,
       };
     };

       row: DetailRow,
       now: Date,
     ): RequestDetailView => ({

     import { Transform, TransformFnParams } from 'class-transformer';
     import { IsInt, Max, Min } from 'class-validator';

     export const DEFAULT_PAGE_SIZE = 20;
     /**
      * A dashboard needs no more, and the bound is what stops one authenticated
     call
      * from pulling the whole table and every piece hanging off it.
      */
     export const MAX_PAGE_SIZE = 100;

     /**
      * Coerces and defaults in one place.
      *
      * @Type(() => Number) is deliberately NOT used: it turns an absent 
     parameter
      * into undefined, which then overwrites the property initializer, and the
      * default silently disappears. Number('') is 0, hence the explicit empty 
     case,
      * which would otherwise be refused by @Min(1) instead of falling back.
      */
     const toPageNumber =
       (fallback: number) =>
       ({ value }: TransformFnParams): unknown =>
         value === undefined || value === null || value === ''
           ? fallback
           : Number(value);

     /**
      * The query of GET /requests.
      *
      * The global ValidationPipe runs with forbidNonWhitelisted, which applies 
     to
      * the query string too: an unknown parameter is a 400 rather than a filter
      * quietly ignored.
      *
      * Messages in French, like every DTO here: they are read by the lawyer.
      */
     export class ListRequestsDto {
       @Transform(toPageNumber(1))
       @IsInt({ message: 'Le numéro de page doit être un entier.' })
       @Min(1, { message: 'La première page porte le numéro 1.' })
       page!: number;

       @Transform(toPageNumber(DEFAULT_PAGE_SIZE))
       @IsInt({ message: 'La taille de page doit être un entier.' })
       @Min(1, { message: 'La taille de page vaut au moins 1.' })
       @Max(MAX_PAGE_SIZE, {
         message: `La taille de page ne peut pas dépasser ${MAX_PAGE_SIZE}.`,
       })
       pageSize!: number;
     }

       /**
        * One page of the lawyer's requests, newest first.
        *
        * The page and its total go through ONE $transaction: read apart, a 
     creation
        * landing between them makes `total` describe a table the page does not 
     come
        * from, and the dashboard shows "3 sur 47" over 46 rows.
        *
        * The pieces are selected rather than counted: two counts on the same
        * relation cannot both be expressed in a single Prisma _count, and B2 
     bounds
        * a request to 20 pieces -- so a page of 20 requests reads 400 tiny rows
     at
        * worst, against the extra round trip a second query would cost.
        */
       async list(
         lawyerId: string,
         query: ListRequestsDto,
       ): Promise<RequestPageView> {
         const where = { lawyerId };

         const [rows, total] = await this.prisma.$transaction([
           this.prisma.depositRequest.findMany({
             where,
             orderBy: { createdAt: 'desc' },
             skip: (query.page - 1) * query.pageSize,
             take: query.pageSize,
             select: {
               id: true,
               title: true,
               createdAt: true,
               items: { select: { file: { select: { id: true } } } },
               links: LAST_LINK,
             },
           }),
           this.prisma.depositRequest.count({ where }),
         ]);

         // One clock reading for the whole page: twenty requests classified 
     against
         // twenty slightly different instants could disagree at a boundary.
         const now = new Date();

         return {
           items: rows.map((row) => toRequestSummary(row, now)),
           page: query.page,
           pageSize: query.pageSize,
           total,
           totalPages: Math.ceil(total / query.pageSize),
         };
       }

       /**
        * One request with its pieces, received or not.
        *
        * findFirst on BOTH criteria rather than findUnique then a comparison: 
     one
        * query, and no branch in which the ownership check can be forgotten. 
     Same
        * shape as PublicLinksService.ownedRequestId.
        */
       async findOne(
         requestId: string,
         lawyerId: string,
       ): Promise<RequestDetailView> {
         const row = await this.prisma.depositRequest.findFirst({
           where: { id: requestId, lawyerId },
           select: {
             id: true,
             title: true,
             createdAt: true,
             items: {
               // The rows share a createdAt to the millisecond, so without this
               // Postgres is free to reshuffle the checklist between two loads.
               orderBy: { position: 'asc' },
               select: {
                 id: true,
                 label: true,
                 file: {
                   select: {
                     originalName: true,
                     mimeType: true,
                     sizeBytes: true,
                     createdAt: true,
                   },
                 },
               },
             },
             links: LAST_LINK,
           },
         });

         if (row === null) {
           throw requestNotFound();
         }
         return toRequestDetail(row, new Date());
       }

  Les décisions qui ne se lisent pas dans le code
