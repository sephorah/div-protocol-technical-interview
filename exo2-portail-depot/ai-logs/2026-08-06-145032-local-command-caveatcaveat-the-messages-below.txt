  peut créer une demande de depot, générer des liens publics expirables à       
  envoyer à son client, et consulter un dashboard; et une page côté client      
  anonyme où il dépose ses pièces.                                              
  Je voulais initialement utiliser Next.js vu qu'il a déjà un système de        
  routing déjà intégré par rapport à React, mais je trouve ça overkill pour     
  juste 2 pages. Ton avis?                                                      

● Ton instinct est bon, mais la meilleure raison n'est pas « 2 pages » — c'est
  que tu as déjà un backend.

  L'argument décisif

  L'intérêt de Next.js, c'est son côté serveur : API routes, server actions,
  RSC, rendu SSR. Or ton serveur, c'est NestJS. Avec Next.js tu te retrouves
  avec deux runtimes Node : un qui fait l'authentification, la validation des
  tokens et la persistance, l'autre qui… fait surtout du proxy vers le premier.
  Tu dupliques la gestion de session, tu ajoutes un hop réseau, et tu dois
  décider pour chaque fonctionnalité « ça vit côté Next ou côté Nest ? ». C'est
  une question que tu n'as pas envie de te poser trente fois dans un projet de
  stage.

  Et les vrais atouts de Next.js ne s'appliquent pas ici :
  - SEO / SSR : un portail privé de dépôt de pièces juridiques ne doit surtout
  pas être indexé. Tu veux noindex, pas du rendu serveur.
  - Performance au premier chargement : population minuscule, utilisateurs
  authentifiés ou porteurs d'un lien. Personne n'arrive via Google.

  Ma recommandation : Vite + React + React Router

  Tu récupères le routing (ta motivation initiale) sans le serveur en trop. Et
  surtout : pnpm build produit un dossier statique que tu sers soit via nginx,
  soit directement depuis Nest avec ServeStaticModule. Un seul processus à 
  déployer, à monitorer, à logger — ce qui simplifie nettement la partie «
  périmètre d'observabilité » de ton livrable.

  Un point à corriger dans ton raisonnement

  « Juste 2 pages » sous-estime le besoin. En pratique tu vas avoir plutôt :

  Côté avocat : login · liste des demandes · création d'une demande · détail
  d'une demande (pièces reçues, liens actifs, révocation)
  Côté client : page de dépôt · lien expiré/révoqué · confirmation d'envoi

  Soit 6 à 8 routes. Ça ne change pas la conclusion — React Router gère ça sans
  effort — mais ça invalide l'argument « le routing ne sert à rien », qui n'est
  pas celui sur lequel je m'appuierais dans ton README.

  Ce qui compte bien plus que le choix du framework

  Tes liens expirables méritent plus d'attention que ton bundler :

  - Token opaque et aléatoire (crypto.randomBytes), pas un JWT — un JWT est
  stateless donc non révocable. Pour des pièces juridiques, l'avocat doit
  pouvoir couper un lien immédiatement.
  - Stocke un hash du token, pas le token en clair : ta base ne doit pas être un
  trousseau de clés.
  - Prévois expiresAt, un compteur d'utilisations, et un flag de révocation.
  - L'endpoint de dépôt anonyme est ta surface d'attaque : rate limiting, taille
  max, validation du type MIME réel (pas juste l'extension).
  - En cas de token invalide, ne divulgue rien sur l'existence du dossier —
  message générique.

  ---
  Ce raisonnement (« pourquoi pas Next.js ») est exactement ce que ton README
  doit contenir dans « architecture et choix justifiés ». Pense à /export avant
  de passer à l'implémentation — cette discussion est précisément le genre de
  trace attendue dans ai-logs/.

  Tes points, un par un

  corepack prepare pnpm@X --activate — cette ligne n'était pas dans mes
  Dockerfiles ; il n'y avait que RUN corepack enable. Mais elle est devenue 
  nécessaire : au premier build en contexte racine, corepack a tiré pnpm 11 et a
  refusé le lockfile 8.x (This project is configured to use 8.12.1). Elle est
  donc désormais aux deux étages, pour deux raisons distinctes :
  - build : corepack s'exécute avant que le moindre packageManager soit dans le
  contexte, il prendrait sinon la dernière version ;
  - runtime : le tarball pnpm est embarqué dans l'image, sinon le conteneur le
  téléchargerait au premier démarrage — dépendance réseau en prod, inacceptable.

  Donc oui, c'est encore une bonne pratique, mais surtout dans l'image finale.
  Alternative plus simple si tu veux te passer de corepack : RUN npm i -g 
  pnpm@8.12.1, même déterminisme, une ligne.

  chown -R node:node /app — supprimé. Il n'existait que pour le bind mount du
  dev. Sans image de dev, il ne sert plus à rien ; USER node seul suffit.

  ENTRYPOINT — appliqué, en forme exec, et pointant sur les scripts de la racine
  : ENTRYPOINT ["pnpm", "run", "start:backend"] / start:frontend.

  Dockerfile de dev — supprimé, ainsi que docker-compose.dev.yml. Le dev passe
  par pnpm dev.

  Ce que ça a impliqué

  Appeler les scripts de la racine oblige à builder depuis la racine (context: 
  ., dockerfile: backend/Dockerfile), puisque le package.json racine doit être
  dans l'image. J'ai ajouté un .dockerignore racine pour ne pas embarquer les
  deux node_modules.

  Côté frontend, start:frontend pointait sur vite preview, qui aurait exigé tout
  le toolchain de dev dans l'image. J'ai donc ajouté serve en dépendance et un
  script start (serve -s dist -l 3000) — preview reste dispo en local.

  Trois choses à savoir

  1. Plus de reverse proxy : nginx est parti avec ta demande « tout sur
  node:22-alpine ». Le navigateur appellera donc l'API en cross-origin → il
  faudra activer CORS côté Nest et une base URL côté front dès les premiers
  appels. Rien n'est cassé aujourd'hui, mais c'est à prévoir.
  2. Les images ont grossi : front 63 MB (nginx) → 307 MB, back 172 → 187 MB.
