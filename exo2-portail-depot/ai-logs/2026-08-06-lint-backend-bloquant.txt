● HTTP vs HTTPS

  C'est le même protocole. HTTPS = HTTP transporté dans un tunnel chiffré (TLS).
  Les requêtes, les en-têtes, les codes de statut sont identiques ; ce qui
  change, c'est ce qu'un observateur du réseau peut lire.

  ┌──────────────────────────┬───────────────────┬─────────────────────────┐
  │                          │       HTTP        │          HTTPS          │
  ├──────────────────────────┼───────────────────┼─────────────────────────┤
  │ Port par convention      │ 80                │ 443                     │

  Trois garanties, pas une seule :

  - Confidentialité — sans TLS, chaque équipement traversé (wifi, FAI, proxy
  d'entreprise) lit l'URL complète, les en-têtes, les cookies, le corps des
  requêtes. Pour ton portail, ça veut dire : les pièces déposées par le client,
  et le token du lien expirable, en clair sur le réseau.
  - Authenticité — le certificat prouve que le serveur qui répond est bien celui
  du domaine. En HTTP, n'importe qui sur le chemin peut se faire passer pour
  lui.
  - Intégrité — en HTTP, un intermédiaire peut modifier la réponse à la volée
  (injection de pub, de script). C'est détecté en HTTPS.

  Ce qui n'est pas caché par HTTPS : le nom de domaine visé et l'adresse IP. Le
  tunnel doit être établi avant que le serveur sache quelle page tu demandes —
  donc sephorah-aniambossou.stage2-div... est visible, /depot/<token> ne l'est
  pas.

  Pourquoi 80 et 443 ?

  Un port n'est qu'un numéro identifiant un service sur une machine (65535
  possibles). Rien de technique ne lie HTTP au 80 : c'est une convention
  enregistrée à l'IANA, et le navigateur l'applique silencieusement. Quand tu
  tapes http://exemple.com, il complète en :80 ; https://exemple.com → :443.
  C'est pour ça qu'on ne les écrit jamais — et que ton :8080 doit être écrit,
  lui.

  Pourquoi deux ports au lieu d'un ? Parce qu'un client HTTPS commence par un
  handshake TLS (ClientHello), et un client HTTP par du texte (GET / HTTP/1.1).
  Historiquement, un serveur ne pouvait pas deviner lequel arrive : deux ports,
  deux comportements. En pratique aujourd'hui, le 80 ne sert quasiment plus qu'à
  rediriger vers le 443 (et à répondre au challenge de renouvellement Let's
  Encrypt).

  Enfin : sur Linux, les ports < 1024 sont privilégiés — seul root (ou un
  binaire avec CAP_NET_BIND_SERVICE) peut s'y attacher. C'est précisément
  pourquoi ton compose publie 8080:80 : 8080 côté hôte, sans droits root ; 80
  côté conteneur, où nginx tourne en root dans son propre namespace.

  Sur ton ./install.sh

  L'exigence est déjà remplie, et vérifiée : Debian 12 vierge, utilisateur
  non-root, ni Node ni pnpm ni nvm → ./install.sh → front 200, deep-link 200,

  vise autre chose :

❯ c'est quoi shellcheck                                                         

● Un linter pour scripts shell. Comme oxlint pour le front ou eslint pour le
  back, mais pour bash : il lit le script sans l'exécuter et signale les pièges
  classiques du shell.

  bash -n, que j'ai lancé, ne vérifie que la syntaxe — que le script est
  grammaticalement valide. Shellcheck va plus loin : il attrape les choses qui
  s'exécutent sans erreur mais ne font pas ce qu'on croit. Les grands classiques
  :

  - variable non entourée de guillemets ($foo au lieu de "$foo") → casse dès
  qu'il y a un espace dans un chemin
  - [ $a = $b ] avec une variable vide → erreur de syntaxe à l'exécution
  - cd /x; rm -rf * → si le cd échoue, le rm s'exécute ailleurs
  - une variable assignée dans un while ... | read → perdue, car le pipe crée un
  sous-shell

  Il porte des codes SCxxxx, et on peut faire taire un cas précis par un
  commentaire — il y en a déjà un dans install.sh:32, # shellcheck 
  disable=SC1091, que j'avais mis pour le source d'un fichier (nvm.sh) qu'il ne
  peut pas suivre.

  Il n'est pas installé sur ta machine, mais l'image Docker évite de toucher au
  système :

❯ pourquoi il y a oxlint ?

● Personne ne l'a choisi — il est arrivé avec le template.

  frontend/README.md est le README stock de Vite, et il parle d'Oxlint. Et
  .oxlintrc.json est mot pour mot la config par défaut du template react-ts.
  Vite 8 a remplacé eslint par oxlint dans ses templates ; le backend/,
  échafaudé depuis le template NestJS, a gardé eslint.config.mjs. D'où deux
  linters dans le dépôt sans que ce soit une décision : c'est juste deux
  templates laissés tels quels.

  Ce qu'est oxlint : un linter écrit en Rust, du projet Oxc (les mêmes qui font
  le transformeur utilisé par @vitejs/plugin-react). Il reprend les règles
  d'eslint mais tourne en parallèle sur tous les cœurs, d'où un gain de vitesse
  important sur les gros dépôts. La contrepartie est que sa couverture de règles
  et son écosystème de plugins restent plus étroits qu'eslint.

  Un point concret, lié aux warnings que tu as : le template recommande
  d'activer les règles type-aware en production (installer oxlint-tsgolint et
  ajouter "options": { "typeAware": true }). Ce n'est pas fait. Sans ça, oxlint
  ne lit que la syntaxe, pas les types — il ne verra jamais un await oublié, par
  exemple, alors que c'est précisément le genre de règle qui produit ton
  warning no-floating-promises côté backend.

  Trois options, du moins au plus intrusif :

  1. Ne rien changer. Deux linters, un par app, chacun idiomatique à son
  template. Ça se défend en une phrase dans le README.
  2. Activer typeAware côté front. Une ligne de config plus une dépendance, et
  le front est enfin vérifié au même niveau que le back.
  3. Unifier sur eslint. Cohérent, mais tu perds la vitesse et tu réécris une
  config qui marche déjà.

  Je te recommande la 2 : c'est la seule qui change quelque chose sur la qualité

❯ ça sert à quoi typeAware                                                      

● Un linter normal ne lit que la forme du code : il parse un fichier en arbre
  syntaxique et applique des règles dessus. Il voit foo(), mais il ne sait pas
  ce que foo renvoie — c'est écrit dans un autre fichier, et il ne le lit pas.

  Les règles type-aware demandent les types au compilateur TypeScript avant de
  juger. Le linter sait alors que foo() renvoie une Promise<void>, ou que telle
  variable ne peut jamais être null.

  L'exemple canonique est justement ton warning backend, main.ts:8 :

  bootstrap();   // renvoie une Promise que personne n'attend

  Syntaxiquement, c'est un appel de fonction irréprochable. C'est uniquement
  parce que la règle connaît le type de retour qu'elle peut dire « tu jettes une
  promesse ». Sans les types, aucun linter ne peut signaler ça.

  Ce que ça attrape, et que la syntaxe seule ne peut pas :

  - await oublié — la fonction rend la main avant que le travail soit fini, et
  une erreur devient une unhandled rejection au lieu d'un catch
  - if (promise) — toujours vrai, un objet Promise est truthy ; le test ne teste
  rien
  - condition toujours vraie — if (user) alors que le type dit que user n'est
  jamais nullable : soit le type ment, soit le test est mort
  - propagation d'any — une valeur non typée qui traverse dix fichiers sans que
  personne le remarque

  Pour ton projet en particulier, c'est la classe de bug qui compte : un portail
  de dépôt, c'est de l'asynchrone partout — upload, écriture disque, base. Un
  await oublié sur un upload, ça donne une réponse « fichier reçu » envoyée
  avant que le fichier soit réellement écrit. Ça marche en test avec un fichier
  de 2 ko, et ça perd des pièces en production.

  Le coût : il faut faire tourner le vérificateur de types, donc c'est nettement
  plus lent qu'un lint purement syntaxique. C'est la raison pour laquelle ce
  n'est pas activé par défaut dans le template, et c'est aussi pourquoi oxlint
  passe par tsgolint — un portage Go du vérificateur, pensé pour que ça reste
  rapide.

  Asymétrie actuelle de ton dépôt : le backend l'a déjà (c'est bien pour ça que
  le warning apparaît), le frontend non.
