  1. Comment marchent les git worktrees

  Un dépôt git normal = 1 dossier = 1 branche à la fois. Un worktree, c'est un 
  deuxième dossier de travail branché sur le même .git.

  # depuis exo2-portail-depot/
  git worktree add ../exo2-a3-minio -b feat/a3-minio
  git worktree add ../exo2-e1-theme -b feat/e1-theme-chakra
  git worktree list      # voir tous les worktrees
  git worktree remove ../exo2-a3-minio   # une fois la branche mergée

  Tu obtiens ../exo2-a3-minio/ qui contient tout le projet sur la branche
  feat/a3-minio, pendant que ton dossier principal reste sur
  feat/a2-modele-de-donnees. Les commits, tags, remotes, le stash sont partagés
  (un seul .git) ; seuls les fichiers de travail sont dupliqués. Une branche ne
  peut être checkout que dans un worktree à la fois — git refuse le doublon, ce
  qui est une sécurité.

  Ce que ça change pour toi : tu lances une session Claude Code par worktree,
  dans un terminal différent. Pendant que l'agent A implémente A3, l'agent B
  implémente E1, et toi tu relis A2. Plus d'attente en série. (Claude Code a
  aussi un outil natif EnterWorktree : si tu me dis « fais ça dans un worktree
  », je le crée et je m'y installe tout seul.)

  Les trois pièges dans ce projet précis :

  Piège: node_modules n'est pas partagé
  Détail: chaque worktree veut son pnpm install dans backend/ et frontend/ (~1
  min)
  ────────────────────────────────────────
  Piège: .env est gitignoré donc absent du nouveau worktree
  Détail: il faut le copier : cp exo2-portail-depot/.env ../exo2-a3-minio/.env
  ────────────────────────────────────────
  Piège: Docker : collision de ports et de noms
  Détail: deux stacks qui bindent 127.0.0.1:21600 → la deuxième meurt. Ta plage
  va jusqu'à 21699 : donne à chaque worktree son offset (21610, 21620…) et son
  projet compose : docker compose -p a3minio up. Sinon compose recycle les
  conteneurs de l'autre worktree.

  Concrètement, la règle : un seul worktree fait tourner la stack docker 
  complète à la fois, les autres travaillent en pnpm dev + pnpm test, ou avec un
  port décalé.

  2. Ce qui est parallélisable après A1/A2

  Deux critères, pas un seul : la dépendance logique et le conflit de fichiers.
  Le second est celui qu'on oublie.

  Indépendants de tout, faisables tout de suite en parallèle :
  - A3 (MinIO) — aucune dépendance, touche compose + un module NestJS neuf
  - E1 (thème Chakra DIV) — 100 % frontend, zéro intersection avec le backend
  - D2 (runner de tests frontend) — isolé, mais à faire avant E1 idéalement pour
  tester les composants
  - A5 (réorganisation infra/) — aucune dépendance mais déplace 
  docker-compose.yml, nginx.conf et install.sh : ça entre en conflit avec A3,
  F1, F2, A6. À faire seul, tôt, et mergé vite.

  Chaîne critique, strictement séquentielle (c'est le cœur produit, chaque
  maillon lit le précédent) :

  A2 → B1 → B2 → B3 → C1 → C2 → B4 → D1

  Rien à gagner à paralléliser là-dedans : B2 a besoin du modèle de A2 et du
  garde de B1, C1 a besoin du token de B3, C2 du storage de A3 et de la session
  de C1.

  Sous-chaînes qui se détachent une fois leur point d'ancrage posé :
  - après C1 : G1 (rate limit) et G2 (audit) en parallèle
  - après C2 : C4 (magic bytes + ClamAV) et G3 (URLs pré-signées) — mais ils se
  marchent dessus (G3 sort le fichier de NestJS, C4 le scanne dedans), donc
  trancher G3 avant d'écrire C4
  - après A5 : A6 → A7 (chaîne infra, indépendante du produit)
  - F1 → F2 : l'endpoint /metrics technique est faisable maintenant, mais les
  métriques métier (tentatives de PIN, dépôts) exigent B/C. Faire F1 tard, sinon
  tu l'écris deux fois.
  - H2 (seed) après B2 ; A8 ferme la marche (il dépend de A3, D1, F2)

  Les faux parallèles, à ne surtout pas lancer en même temps : A5 avec quoi que
  ce soit qui touche compose ; A4 (.env.example) avec A3/B1/F1, puisque ce sont
  eux qui créent les variables — A4 devient une simple passe de vérification en
  fin de parcours.

  Objectivement : non, pas maintenant

  Trois jours, en retard, jamais utilisé de worktree — la réponse honnête est
  non. Les raisons, dans l'ordre d'importance :

  1. Ton chemin critique est séquentiel de toute façon. A2 → B1 → B2 → B3 → C1 →
  C2 → B4 c'est le gros du travail restant, et rien là-dedans ne se
  parallélise. Le worktree ne t'achèterait que A3, E1 et A5 en recouvrement —
  soit peut-être une demi-journée de gain théorique.

  2. Le coût est immédiat, le gain est différé. Par worktree : pnpm install ×2,
  copier .env, décaler les ports docker, se souvenir de quel terminal est sur
  quelle branche. Puis les merges. Un conflit git sur schema.prisma ou
  docker-compose.yml quand tu découvres l'outil et qu'il te reste 12 h, c'est
  exactement le scénario qui coûte la soirée.

  3. Le vrai goulot n'est pas le parallélisme, c'est ta relecture. Même avec
  trois agents qui produisent en parallèle, c'est toi qui valides — et tu es le
  processus mono-thread. Trois branches en attente de relecture ne vont pas plus
  vite qu'une, elles ajoutent juste du contexte à tenir en tête.

  Ce que je ferais à ta place

  Séquentiel, une seule branche à la fois, dans l'ordre du plan. Et surtout :
  coupe le périmètre maintenant, pas dans 60 heures. P0 uniquement — A2, A5,
